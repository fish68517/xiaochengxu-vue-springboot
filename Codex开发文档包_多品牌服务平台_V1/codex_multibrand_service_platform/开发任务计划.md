# 多品牌服务平台开发任务计划

> 制定日期：2026-08-30

> 后续编码唯一目录：`E:\bishe27\服务平台小程序\code`

## 1. 计划结论

当前 `code` 目录不是空项目，也不是需要推倒重建的原型。现有代码已经具备三端、uniCloud 云函数、本地镜像后端、订单状态机、支付、退款、钱包、提现、异议以及测试基础。后续应继续沿用以下结构增量开发：

- `apps/client`：客户小程序与 H5 下单/支付页；
- `apps/workbench`：客服与接单人员 Web 工作台；
- `apps/admin`：管理后台；
- `packages/domain`：订单、佣金、钱包、品牌等领域规则单一源；
- `packages/backend`：本地开发和自动化测试使用的镜像后端；
- `uniCloud-tcb/cloudfunctions/game-service`：生产云函数 action 入口；
- `uniCloud-tcb/database`：uniCloud 数据库 schema；
- `scripts`：构建、联调、部署和验证脚本。

实施策略是“保留可用能力，先修基线和跨品牌安全，再补齐业务闭环与管理页面”。不新建另一套项目，不复制品牌业务代码，不整体替换 Vue、uni-app、uniCloud 或现有领域层，也不为追求目录形式而强制迁移成文档示例中的新 Monorepo。

## 2. 范围与硬边界

### 2.1 本计划范围

- 三端共用同一后端的多品牌服务平台；
- 品牌配置、品牌资产、商品和数据隔离；
- 客户下单、H5 支付、订单履约、完成核对和结单；
- 抢单、指派、改派及操作历史；
- 佣金账本、退款追佣、提现审批、异议仲裁；
- RBAC、品牌权限、审计、幂等和并发安全；
- development、staging、production 环境与发布验证；
- 自动化测试、构建、冒烟和验收证据。

### 2.2 明确不做

- 不重新创建 `customer-miniapp`、`payment-h5`、`workbench-web` 等平行应用；现有 `apps/client` 已承载小程序和 H5，应继续复用；
- 不把现有 JavaScript 一次性重写为 TypeScript；类型检查能力可增量接入；
- 不复制多套页面来支持不同品牌；
- 不在业务规则未确认时猜佣金比例、退款条件、仲裁 SLA；
- 不在 development 中误用生产支付密钥；
- 不把前端传入的 `brandId`、金额或目标订单状态当作后端权威数据；
- 不删除当前 12 个订单主状态、26 个现有业务集合/schema 或旧兼容路由，除非迁移完成并有回归证据。

## 5. 实施前业务确认项

以下事项必须形成书面结论；在确认前只搭建可配置结构和测试数据，不写死正式规则：

1. 现有 V1.1 的 12 状态是否仍是正式订单状态。建议保留 12 状态，通过 `verification` 子状态和独立 action 拆分“完成提交、核对、结单”，避免大规模迁移；
2. 佣金对象、规则、冻结期、可用时点、税费和版本生效方式；现有种子数据 20% 只能标记 `DEMO_ONLY`；
3. 未开工、服务中、未达标、仲裁退款的正式条件，以及负余额追佣后的处置规则；
4. 提现是“审核通过即打款”还是“审批与出款分离”。按合并文档默认应分离；
5. 异议原因码、双方举证时限、仲裁 SLA 与裁决类型；
6. 每个品牌使用独立商户号还是共享商户号，以及服务号、小程序、支付渠道之间的合法绑定；
7. 品牌管理员、财务、仲裁、调度角色是否允许一人多角色，以及跨品牌授权流程；
8. 旧数据应归属哪个默认品牌，以及上线时是否存在无 `brandId` 的历史订单。

这些确认项不阻塞 Batch 0～2 的工程基线和安全改造，但会阻塞对应资金规则和正式生产发布。

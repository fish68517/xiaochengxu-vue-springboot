# 第二阶段代码修改任务

## 1. 文档目的

本文以《手动测试用例》42 项、`docs/code-audit/TEST_CASE_MATRIX_V2.md` 和当前代码为依据，规划 P0～P2 修复完成后的下一轮增量开发。

本轮不推倒重来，继续沿用现有 uni-app 三端、`game-service`、`system-runner`、领域包、Repository、数据库集合和部署脚本。编码仍在 `code` 目录内完成。

本文只安排需要编写或调整的生产代码、配置清单和发布工具，不安排新增 test case 文件。每个任务完成后只运行现有检查、构建和发布前门禁，作为回归依据。

## 2. 当前结论

### 2.1 已完成基线

- 42 个用例均已存在对应代码链路，当前没有 `MISSING`、`PARTIAL`、`REQUIREMENT_MISMATCH` 或已知 `SECURITY_RISK`。
- 28 项为 `PASS_CODE`。
- 6 项仍需部署或真机人工验收：TC05、TC13、TC27、TC39、TC41、TC42。
- 8 项受微信等外部服务约束：TC03、TC04、TC09、TC15、TC18、TC19、TC20、TC36。
- 当前既有检查基线为 `npm test` 255/255，Client、Workbench、Admin 的 H5 构建均通过。

### 2.2 本轮真正需要补强的代码

剩余 14 项并不等同于 14 个“缺失功能”。其中支付、退款、订阅消息和微信回调最终必须由真实商户、服务号、模板、域名及云空间验证；代码侧需要做的是补齐真实环境下的状态恢复、幂等、并发、可观测性和发布前校验，避免一接真实环境就暴露假成功、重复消费或无法定位的问题。

当前源码中可确认的重点改进点如下：

1. 微信内 JSAPI 返回成功后，H5 页面会直接进入成功页，应改成以服务端支付单状态为最终依据。
2. MWEB 仅保存简单的 `paymentId/orderNo/ts`，缺少过期、有限轮询、页面恢复和重复发起保护。
3. OAuth 使用固定 `state=order`，`oauthExchange` 只接收 `code`，缺少一次性 state 校验和订单上下文绑定。
4. 小程序订阅授权把业务模板键 `ORDER_STATUS_UPDATE` 直接作为 `tmplIds`，真实微信环境应使用实际模板 ID，业务模板键只用于后端映射。
5. `subscribe_quota` 已有条件扣减，但索引清单缺少订单与模板维度的唯一约束。
6. 退款回调会修改退款单、订单和钱包，但最终状态日志、失败原因、补偿结果还需要形成完整统一的业务留痕。
7. `partial_progress` 退款比例仍需由可信进度证据和服务端规则约束，不能把前端传入比例直接视为最终事实。
8. 三个超时扫描仍会读取某状态下的全部订单；定时任务缺少持久化运行状态、失败摘要和后台可见的健康状态。
9. 品牌保存是“查询版本后直接更新”，没有 `expectedVersion` 条件更新；多人同时编辑时存在后保存覆盖先保存的风险。
10. 品牌客户端缓存只有 TTL 和手动清除，缺少轻量版本探测，后台发布后无法稳定做到三端及时刷新。
11. 静态托管脚本能部署三个入口，但尚未用统一清单校验 SPA 回退、目录前缀、缓存策略和入口互不覆盖。
12. Dashboard、报表和补偿任务仍有整集合读取后再内存过滤的路径，数据量增长后容易触发云函数超时或资源耗尽。

# 第一阶段：交易与调度闭环加固

## Batch 1-1：微信支付状态真值与 H5 恢复

### 修改范围

- `apps/client/src/pages/h5-order/index.vue`
- `apps/client/src/api.js`
- `apps/client/uniCloud-aliyun/cloudfunctions/game-service/lib/oauth.cjs`
- `apps/client/uniCloud-aliyun/cloudfunctions/game-service/lib/payment-operations.cjs`
- `apps/client/uniCloud-aliyun/cloudfunctions/game-service/lib/services.cjs`
- `uniCloud-tcb/cloudfunctions/game-service/lib/` 中对应生产文件
- 如需新增一次性 OAuth state 数据，补充两套云空间的 schema 和索引清单

### 代码任务

1. 将 JSAPI 回调成功定义为“微信收银台已返回”，不能直接显示业务支付成功。
2. JSAPI 返回 `ok` 后保存待确认支付上下文，并调用 `getPaymentStatus`；只有服务端返回 `SUCCESS` 才进入成功页。
3. 对 `PENDING/PROCESSING/FAILED/CLOSED` 分别显示明确状态，避免把网络失败、用户取消和支付失败混为一个提示。
4. 重构 H5 待支付记录，至少保存：`orderId`、`orderNo`、`paymentId`、`payType`、`createdAt`、`expiresAt`、`retryCount`。
5. 在 `onShow`、浏览器 `pageshow` 和 `visibilitychange` 恢复时查询支付状态；采用有限次数和指数退避，不做无限轮询。
6. 待支付记录过期后停止自动查询，允许用户手动刷新状态或重新发起支付。
7. 重新发起支付前先查询原支付单；原单已成功则直接展示成功，仍处理中则继续等待，已关闭或失败才创建新的支付参数。
8. 增加 OAuth state 创建与校验：state 必须一次性、短时有效，并绑定 H5 token、订单或当前跳转上下文；移除固定 `state=order`。
9. `oauthExchange` 同时接收 `code + state`，服务端校验通过后再换取 openid；state 重放、过期或上下文不一致均拒绝。
10. 保持写操作现有幂等键，不对支付创建、确认等写操作进行无条件自动重试。

### 完成条件

- 页面不再仅凭 `WeixinJSBridge` 返回值展示支付成功。
- 刷新、切后台再返回、MWEB 回跳后均能恢复同一支付单查询。
- 同一订单反复点击不会生成不可控的并行支付流程。
- OAuth state 不再是固定字符串，且只能使用一次。

## Batch 1-2：订阅消息配置与额度一致性

### 修改范围

- `apps/client/src/subscribe.js`
- `apps/client/src/api.js`
- Client 构建环境示例文件
- 两套 `game-service/lib/subscribe.cjs`
- 两套 `game-service/lib/services.cjs`
- 两套 `database/brand-indexes.json`
- `docs/deployment/UNICLOUD_INDEXES.md`

### 代码任务

1. 新增前端实际模板 ID 配置，例如 `VITE_WECHAT_SUBSCRIBE_ORDER_STATUS_TEMPLATE_ID`。
2. `uni.requestSubscribeMessage({ tmplIds })` 必须传微信后台生成的模板 ID，不再传业务模板键。
3. 前端授权成功后仍向后端提交稳定业务键 `ORDER_STATUS_UPDATE`，由后端按品牌和环境解析真实模板 ID。
4. 发布前门禁检查前后端模板配置是否存在，并校验当前品牌是否有模板映射；不得输出 secret 或完整 access token。
5. 在 `subscribe_quota` 增加 `orderId + templateKey` 唯一索引；若设计允许一单多次订阅，则改为引入 `grantId` 并以 `grantId` 唯一，二者只能选择一种明确协议。
6. 将额度状态从单一 `usedAt` 扩展为可诊断状态：`AVAILABLE/SENDING/USED`，同时记录 `attemptCount`、`lastAttemptAt`、`lastErrorCode`。
7. 发送前使用条件更新领取额度；发送成功后转为 `USED`；明确失败时回补为 `AVAILABLE`；结果不确定时保持 `SENDING`，交给补偿任务查询或限次重试。
8. 通知记录写入 `brandId`、`orderId`、`templateKey` 和稳定错误码，便于后台定位单个订单通知状态。
9. 保持“用户拒绝订阅不影响下单”的现有产品规则。

### 完成条件

- 微信前端申请授权使用真实模板 ID，后端仍以业务模板键组织逻辑。
- 并发发送不能重复消费同一授权额度。
- 发送失败、未知和成功均可从数据库记录中定位，不阻塞订单主流程。

## Batch 1-3：退款状态、进度证据与资金留痕

### 修改范围

- `packages/domain/src/order-machine.js`
- `packages/domain/src/index.js`
- `scripts/build-domain.mjs` 生成的两套 `domain.cjs`
- 两套 `game-service/lib/payment-operations.cjs`
- 两套 `game-service/lib/services.cjs`
- `refunds`、`order_logs`、`audit_logs`、`wallet_transactions` 相关 schema
- Admin 退款审批详情页及 API（只补状态、证据和补偿入口，不重做页面）

### 代码任务

1. 统一退款状态落库方法，退款申请、审批、调用微信、回调成功、回调异常、主动查单、补偿成功/失败都使用同一状态转换入口。
2. 每次最终状态变化必须同时具备：退款单状态、订单状态、`order_logs`、`audit_logs`；涉及佣金追回时还必须有唯一 `wallet_transactions`。
3. 对微信回调建立事件幂等键，优先使用微信事件 ID；无法取得时使用通知报文摘要。重复回调只返回成功，不重复退款、不重复追回佣金。
4. 对退款金额做三重校验：退款单金额、原支付金额、微信通知金额与币种必须一致。
5. `partial_progress` 增加可信进度快照，至少包含服务总量、已完成量、计量单位、证据附件 ID、提交人和提交时间。
6. 退款比例由服务端根据可信进度计算，前端传入比例只能作为申请值；超范围、缺证据、证据不属于当前订单时拒绝审批。
7. 保留人工仲裁能力，但管理员修改最终比例时必须填写原因并写审计前后值。
8. 对 `PROCESSING/ABNORMAL/queryRequired` 退款提供受权限保护的“查询微信状态/重新执行补偿”后端 action；仅财务或管理员可用，不能直接重复发起退款。
9. 补偿任务使用同一个 `outRefundNo` 查询，绝不为同一退款单生成第二个微信退款单号。
10. Admin 退款详情显示本地状态、微信状态、最后错误码、最后查询时间、佣金追回金额和可执行操作。

### 完成条件

- 同一退款请求、回调或补偿执行多次，订单和钱包结果保持一致。
- 部分进度退款不再只依赖前端自由填写比例。
- TC15、TC18、TC19、TC20、TC36 对应代码具备完整可追踪链路；其真实退款结果仍以微信商户环境验收为准。

## Batch 1-4：定时任务可部署、可观测、可补偿

### 修改范围

- 两套 `cloudfunctions/system-runner/index.js`
- 两套 `game-service/lib/services.cjs`
- `scripts/deploy-unicloud.mjs`
- `scripts/release-preflight.mjs`
- 新增机器可读的定时任务清单，例如 `config/system-runner-tasks.json`
- 新增任务运行记录集合及两套 schema/索引
- Admin 运维状态页面或现有运营页面

### 代码任务

1. 以机器可读清单维护三个任务：支付超时关闭、抢单池超时标记、指派超时拒绝；清单包含 action、建议 cron、超时阈值来源和是否启用。
2. `system-runner` 每次执行生成 `runId`，记录 action、开始/结束时间、扫描数、变更数、失败数、耗时和稳定错误码。
3. 任务并发执行时使用租约或运行锁，避免同一 action 在多个触发实例中重叠扫描。
4. 扫描改为按截止时间、状态和主键分页，不再一次加载该状态的全部订单。
5. 支付、入池、指派超时字段在订单进入对应状态时固化快照；扫描只使用快照与截止时间，配置变更不追溯破坏已有订单。
6. 为扫描补充联合索引，至少覆盖 `status + payDeadline`、`status + poolDeadline`、`status + assignmentDeadline`；实际字段名在编码时统一后再写入两套索引清单。
7. 单条订单处理失败不能中止整批；记录失败订单 ID、错误码和下一次重试时间，不记录客户敏感字段。
8. Admin 增加只读任务健康状态：最近成功时间、最近失败时间、连续失败次数、最近处理数量。手动执行必须沿用现有内部鉴权并限制管理角色。
9. `deploy-unicloud.mjs` 在上传前校验任务清单、函数目录、环境变量名称和两套云端产物一致性；无法由 CLI 创建触发器时明确输出控制台待办，不伪造“已部署”。

### 完成条件

- 三个任务均可从运行记录判断是否真实执行成功。
- 大量订单下采用分页扫描，不再整集合加载。
- 重复触发、任务重叠和单条失败不会导致重复状态迁移。
- TC05、TC13、TC27 仍需云控制台实跑，但仓库可直接给出准确配置并收集执行证据。

7. 记录 action、brandId、耗时、错误码、重试次数和 traceId，告警内容不得包含手机号、微信号、token 或支付密钥。

# 第二阶段：品牌发布与多端交付加固

## Batch 2-1：品牌配置并发控制与发布协议

### 修改范围

- `apps/admin/src/pages/brands/index.vue`
- `apps/admin/src/api.js`
- `apps/client/src/brand.js`
- Workbench/Admin 的品牌初始化代码
- 两套 `game-service/lib/services.cjs`
- `brands`、`brand_config_versions` schema 和索引

### 代码任务

1. `saveBrandConfig` 增加 `expectedVersion`，服务端使用条件更新实现 CAS；版本不一致返回稳定错误码 `BRAND_VERSION_CONFLICT`。
2. 新建品牌从版本 1 开始；修改品牌必须基于管理员加载时的版本，禁止“查询后普通 update”覆盖并发修改。

4. 明确草稿与发布语义。若继续采用“保存即发布”，接口和页面统一称为发布；若增加草稿，则只有发布 action 才更新 `publishedVersion`。

- 两名管理员同时编辑时，后提交者收到版本冲突而不是静默覆盖。
- 每次发布都可查到不可变快照、操作者和审计记录。
- 回滚产生新版本，不修改历史版本记录。

## Batch 2-2：品牌配置主动刷新

### 修改范围

- 三端品牌加载模块
- Client `apps/client/src/brand.js`
- `getBrandConfig` 及新增的轻量版本查询 action
- 页面生命周期和网络恢复钩子

### 代码任务

1. 新增轻量 `getBrandConfigVersion`，返回 `brandId/publishedVersion/updatedAt`，不返回完整配置。
2. 三端缓存键必须包含品牌标识和发布版本，避免不同品牌共用同一缓存。
3. 首屏可先使用未过期缓存渲染，再后台探测版本；版本变化时获取完整配置并原子替换。
4. 在应用启动、`onShow`、浏览器恢复可见和网络恢复时执行有限频率的版本探测。
5. 完整配置请求失败时保留最近一次有效品牌配置，并展示非阻断提示；不能回退到其他品牌数据。
6. 发布后的主题、Logo、Banner、文案和客服联系信息通过统一品牌状态更新，不允许各页面自行缓存副本。

### 完成条件

- 后台发布后，三端无需重新构建即可在下一次前台恢复或版本探测时更新。
- 网络失败不会造成白屏，也不会把 A 品牌缓存展示给 B 品牌。

## Batch 2-3：三入口静态托管与路由隔离

### 修改范围

- `scripts/deploy-hosting.mjs`
- `scripts/release-preflight.mjs`
- 三端 Vite/uni-app H5 base 配置
- 新增托管清单，例如 `config/hosting-targets.json`
- 三端入口鉴权和错误页

### 代码任务

1. 用统一清单声明 Client `/`、Workbench `/workbench/`、Admin `/admin/` 的构建目录、部署空间、路由前缀和 SPA fallback。
2. 部署前检查三个构建目录均存在，`index.html` 和静态资源路径均使用正确 base，禁止包含 `127.0.0.1`、`localhost` 或开发端口。
3. 检测部署目标覆盖关系；后台两个前缀不能被 Client 根目录部署误删或覆盖。
4. 为 `index.html` 和带 hash 静态资源分别定义缓存策略：入口短缓存或不缓存，hash 资源长缓存。
5. Workbench 与 Admin 启动时校验当前入口和角色；进入错误入口时跳转到对应登录页或展示 403，不加载越权业务页面。
6. 后端权限仍作为最终边界，前端路由隔离只负责体验，不能替代 action 授权。
7. 部署脚本输出实际目标空间、前缀和待人工配置的域名/CDN事项，执行前不打印 secret。

### 完成条件

- 三端构建产物不会因错误 base 产生资源 404。
- 重复部署任一入口不会破坏另外两个入口。
- 客户、客服、接单人员和管理员从错误入口进入时行为明确，后端仍拒绝越权 action。

## Batch 2-4：手机浏览器与页面生命周期加固

### 修改范围

- Client 公共布局、H5 下单页、订单页
- Workbench 登录、订单详情、接单池、钱包、资料页
- Admin 登录及主要表格/表单页
- 三端公共状态组件和样式变量

### 代码任务

1. 使用 `100dvh` 并保留 `100vh` 回退，处理浏览器地址栏伸缩造成的页面跳动。
2. 统一安全区：顶部和底部使用 `env(safe-area-inset-*)`，固定按钮和 Tabbar 不遮挡内容。
3. 表单在软键盘弹出时保持当前输入项可见，提交按钮不被键盘或浏览器底栏覆盖。
4. 主要点击区域不小于移动端可操作尺寸；不把 hover 作为唯一交互方式。
5. 弹窗、抽屉和长表单统一滚动锁，关闭后恢复原滚动位置。
6. 长订单号、昵称、错误信息和金额采用换行或省略策略，避免横向溢出。
7. 统一加载、空数据、网络失败、权限失败和服务繁忙状态；保留可恢复操作，不自动重复提交写请求。
8. 对微信内浏览器、Android 系统浏览器、iOS Safari 的页面恢复事件使用同一生命周期适配，重点承接支付状态恢复。
9. 列表首屏使用分页和骨架状态，避免等待整表数据后才渲染。

### 完成条件

- 360px～1440px 宽度下无关键内容横向溢出。
- 手机软键盘、底部安全区和浏览器返回前台不会破坏支付或表单状态。
- 网络与资源耗尽提示可恢复且不会重复下单、退款或提现。

## Batch 2-5：性能追踪与统一发布门禁

### 修改范围

- 三端 API Adapter
- `game-service/index.js`、Repository 和主要查询 service
- 现有运营事件、告警、容量与发布前检查脚本
- `scripts/release-preflight.mjs`
- 新增云产物一致性检查脚本

### 代码任务

1. 为每次请求生成或透传 `traceId`，云函数响应和错误均返回同一 traceId，便于前后端关联排查。
2. 记录 action、brandId、角色、结果码、耗时和扫描/返回数量；禁止记录 token、密码、手机号明文、微信号和支付密钥。
3. 为订单、报表、钱包、退款、通知和任务运行接口统一分页协议：`limit + cursor + hasMore`，限制最大页大小。
4. Repository 增加可复用的条件查询、排序、分页和聚合能力，业务层不再反复复制“全表读取后过滤”。
5. 为首屏、品牌配置、支付状态恢复记录关键耗时；慢请求进入运营事件，达到阈值时进入现有告警通道。
6. 新增云产物一致性检查，覆盖阿里云与腾讯云的 `auth.cjs`、`services.cjs`、支付、订阅、system-runner、domain 产物、schema 和索引清单。
7. 发布前门禁统一检查：三端构建目录、环境组合、品牌配置、真实模板 ID、支付/退款回调 URL、定时任务清单、索引清单、云产物一致性和本机地址泄漏。
8. 门禁只判断仓库与配置是否就绪；微信真实支付、域名生效、触发器运行和真机表现继续保留为人工/外部验收，不自动标记通过。

## 5. 实施纪律

1. 不重写现有订单状态机；新增状态或字段必须先落在 `packages/domain`，再由构建脚本同步到两套云函数。
2. 不把本地 `scripts/api-server.mjs` 的 Memory DB 行为当作生产实现；本地镜像只用于保持契约一致。
3. 阿里云与腾讯云生产文件必须由明确的源或同步脚本维护，禁止只修改一份。
4. 数据库字段变更必须同步 schema、索引清单和迁移脚本；迁移必须支持重复执行。
5. 任何支付、退款、钱包和提现写操作都必须使用稳定业务幂等键，并保留审计记录。
6. 不删除现有登录、会话、角色、品牌范围、MFA、PII 或内部调用鉴权能力。
7. 不上传 uniCloud、不发布 H5、不修改真实环境变量；编码完成后由部署阶段按清单执行。
8. 不因源码和构建通过就把外部项目标记为 `PASS_CODE` 或 Production Ready，必须保留真实环境验收边界。

# 微信支付文件读取实施方案

日期：2026-09-12  
范围：阿里云 uniCloud `game-service`，普通直连商户、微信支付公钥模式。  
状态：阶段 A 已实施；阶段 B 本地真实支付文件已准备并通过校验，尚未上传部署或进行真实付款。已确认品牌 Code 为 demo-a、目标回调为 https://api.qmhyplayer.com/pay-notify；后台引用仍须保存对齐。

## 一、目标与原则

将尚未配置的支付凭据（包括 APIv3 密钥）改为从云函数服务端文件读取，不再要求逐项新增环境变量。已经配置且有效的云端变量保留，不重复迁移、不自动删除。

必须保持现有品牌隔离、支付快照、签名、通知验签、解密、金额校验和幂等处理，不重写订单流程，不更改 `uniCloud-tcb`。

uniCloud 每个函数最多 20 个环境变量，单个值最长 1024 字符。现有商户私钥约 1704 字符，不能直接完整存入单个变量；本方案也不采用拆分私钥或把所有 PEM 塞进 JSON 环境变量的做法。参见[环境变量官方限制](https://doc.dcloud.net.cn/uniCloud/cf-env-variables.html)。

**安全边界：**文件读取不是加密保管。私钥/APIv3 密钥将存在服务端部署包中，能下载或查看云函数源码的人可能取得凭据。仅允许指定运维人员访问，禁止放进前端、公开云存储、客户交付压缩包或 Git。后续有更高要求时再迁移至专用秘密管理服务。

### 3.2 credentials.json

按环境和既有前缀组织凭据，避免测试环境、生产环境串用：

```json
{
  "production": {
    "PAY_XINGHE": {
      "SERIAL_NO": "28CC3DF92D6CEF5D7B22C7B426FD8C9A9F317E1B",
      "PRIVATE_KEY_FILE": "merchants/1116677386/apiclient_key.pem",
      "MERCHANT_CERT_FILE": "merchants/1116677386/apiclient_cert.pem",
      "APIV3_KEY": "实施时从受控文件读取填入，禁止提交",
      "NOTIFY_URL": "待确认的实际HTTPS云函数支付回调地址",
```

## 四、环境变量与文件的优先级

### 4.1 品牌映射

1. 存在非空 `WECHAT_PAY_CONFIG_MAP`：完整采用其映射，不与文件映射合并。
2. 未配置该变量：读取固定位置 `private-config/wechat-pay.json`。
3. 选中的来源 JSON 错误、环境不存在或品牌不存在：明确报错，不切换来源“救场”。

这样已配置的云端映射不受影响，也不会意外把文件里的其他品牌开放到生产环境。

### 4.2 凭据字段

每个字段按“选中品牌的 `envPrefix` 对应非空环境变量 → 当前环境和前缀下的文件字段”读取。例如已有 `PAY_XINGHE_APIV3_KEY` 则继续使用，不重复写入真实 JSON；没有才用 `credentials.json` 的 `APIV3_KEY`。

PEM 对应关系：`PAY_XINGHE_PRIVATE_KEY` 优先，否则使用 `PRIVATE_KEY_FILE`；公钥、平台证书同理。普通标量包括 `SERIAL_NO`、`APIV3_KEY`、`NOTIFY_URL`、`PUBLIC_KEY_ID`、`PLATFORM_SERIAL`。

已配置但无效的环境变量应报错，不悄悄用文件覆盖。仅空字符串视为未配置；空白内容应作为无效配置处理。诊断只显示字段名及来源 `environment/file`，不显示值。

选择后必须检查成套一致性，避免环境中的旧序列号搭配文件中的新私钥。微信公钥和 ID 的对应关系不能从 PEM 独立推导，仍需平台核对及真实验签。

不向 `process.env` 写回读取结果，而是构造局部标准化对象，继续传给 `Pay.createClient({ env })`，防止跨品牌污染。保持 `resolvePaymentConfig` 返回的 `{ env, snapshot }` 接口；快照不得新增密钥或 PEM。

### 4.3 不迁移的配置

`OAUTH_APPID/OAUTH_SECRET`、`WECHAT_MP_APPID/WECHAT_MP_SECRET`、会话密钥、PII 加密密钥及业务开关保留原逻辑。它们不是本次新增支付文件读取的范围。已经部署的支付变量也不主动删除。

本方案不要求增加环境变量；是否精简冗余变量可以后续单独处理。

## 五、加载器校验与错误处理

- 文件仅允许固定目录内的相对路径；拒绝绝对路径、`..`、盘符、UNC、URL。对 `realpath` 结果再次确认目录边界，禁止符号链接越界。
- JSON 使用 UTF-8，允许去除文件开头 BOM；限制 JSON 文件至 256 KiB、单个 PEM 至 32 KiB。密钥正文不随意 trim 或改写。
- 只按需读取缺失字段的文件；全部由环境提供时不要求真实文件存在。存在但内容错误的已选配置不能静默忽略。
- `crypto.createPrivateKey` 校验商户 RSA 私钥；`X509Certificate` 检查商户证书 CN、有效期、序列号及私钥匹配；公钥检查 RSA 类型和位数，至少 2048 位。
- 文件模式要求提供商户证书供配套检查；纯旧环境配置模式保持既有兼容，不强制新增文件。混合模式如有证书必须校验最终选中的私钥和序列号。
- APIv3 密钥必须为 32 字节；生产回调必须是明确配置的公网 HTTPS 地址，不回退到 `wechat-pay.cjs` 的示例默认域名。
- 保留现有跨主体禁止共享凭据、AppID 绑定声明、品牌引用、后台商户号一致性校验；声明绑定不等于已在微信平台绑定。
- 错误按缺文件、JSON 格式、缺字段、证书不匹配等分类，服务端只记录错误码/字段名/品牌标识；不返回密钥、文件正文或完整文件系统路径给客户端。
- 不开放读取凭据的 HTTP/action 接口；不把凭据放到订单、品牌接口、日志或审计快照。
- 第一版不缓存解析后的支付配置，避免环境变量更新后读取旧值；单次业务操作内复用结果。以后若优化缓存，必须定义失效与轮换机制。

1. 检查 Git 现状、局部指引及真实文件是否已经被追踪；先添加精确忽略规则 `/code/apps/client/uniCloud-aliyun/cloudfunctions/game-service/private-config/`。现有 `*.pem` 不会保护含 APIv3 密钥的 JSON。
2. 新增 `payment-config-files.cjs` 和不含真实凭据的模板，完成受限读取、来源选择、错误脱敏及校验。
3. 改造 `payment-config.cjs`，抽出统一映射入口（例如 `loadPaymentMap`），保留外部函数签名与 snapshot 结构。
4. 同步修改 `payment-operations.cjs` 的 `clientFor`、`decodeNotification`：从统一入口选配置、枚举获准品牌。无环境映射但存在文件映射时不能进入开发旧分支；正式环境仍禁止 mock。通知候选数量超限须明确报错，不静默遗漏品牌。
5. 检查 `services.cjs` 和所有支付调用方，不允许遗留直接读取映射变量的业务分支。保留原支付幂等键及订单状态逻辑。
6. 核对 `wechat-pay.cjs` 的公钥模式请求头：当前 `authHeaders` 只返回 Authorization，需按官方公钥接入规则补齐 `Wechatpay-Serial` 的微信支付公钥 ID，不能误填商户证书序列号；签名 Authorization 仍使用商户证书序列号。保持响应验签、通知先验签后解密及退款流程。
7. 使用临时生成的测试密钥完成最小验证：旧环境模式、纯文件模式、混合优先级、JSON 错误、缺文件、路径越界、证书不匹配、APIv3 长度、跨品牌隔离，以及文件映射下的支付/退款通知入口。真实凭据不进入测试代码。

### 阶段 B：真实配置与部署验收

1. 先确认实际品牌 Code、主体标识、品牌 secretRef、真实 `/pay-notify` URL。缺失选择时只完成代码与模板，不猜测发布配置。
2. 只核对已有云端支付变量的名称、存在状态和必要的匹配结果，不批量导出密钥；无法访问云端时请用户提供变量名称清单，不能声称已确认远端配置。
3. 在受控本地目录准备实际文件；已有有效云端变量对应字段不重复迁移。严禁把秘密写入可提交模板、说明文档或工具输出。
4. 使用 `git check-ignore` 验证忽略，`git ls-files` 确认真正未追踪。已追踪文件不能仅靠新增忽略规则解决，需报告并单独处理历史泄露及轮换。
5. 通过 HBuilderX 上传阿里云 `game-service` 整个函数目录及依赖。检查部署流程没有把被 Git 忽略的 `private-config` 排除；不要假设“Git 忽略”和“部署忽略”是同一件事。
6. 云端用非敏感配置诊断确认文件可读取；诊断不应创建公开凭据查询入口。保持原生产变量，不关闭验签，不切换 mock。
7. 真机测试小额订单：预支付请求成功、应答验签成功、调起收银台、支付通知验签和解密成功、金额/商户/AppID 匹配、订单自动更新；再检查重复通知、取消重付、查询和退款。
8. 记录实际发布版本与验收结果。本次只涉及服务端配置读取，不应要求重发客户小程序或管理 H5，除非实施中发现必要前端改动。

## 七、回滚与交付标准

文件配置变化需重新上传函数。发布前保留访问受限的上一版本函数包和配置，不能放入普通 Git 或公开备份。

回滚必须恢复匹配的代码与配置：旧代码只读环境变量，不能单独回滚代码后期待新文件继续生效。若旧版本没有完整支付配置，停止新支付并报告，不以 mock 或跳过校验替代。尚未结束的订单、退款和通知所需旧凭据不能随意删除；凭据轮换需要单独安排过渡。

交付判定：

- 不新增必需环境变量即可完成文件模式配置。
- 已有环境模式可用，优先级可解释，错误不静默回退。
- 下单、查单、退款和通知统一读取，品牌隔离及幂等不退化。
- 私钥/APIv3 未进入 Git、前端、日志和用户响应；部署包权限受控。
- 本地测试通过仅代表实现校验通过；只有真实付款、验签、解密与状态闭环完成，才标记“支付接入通过”。

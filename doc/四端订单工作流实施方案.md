# 四端订单工作流实施方案

## 当前联调策略（2026-09-13 更新，优先于下文历史授权步骤）

### 客服录入提示“无权执行”的补充排查

本次提供的 `enterOrder` 请求中，会话主角色及角色列表都是 `WORKER`，品牌范围已是 `*`。所以失败发生在角色权限校验，不是品牌授权，也不是“早上8：00”等录入字段校验。

正确规则：客服/管理员可将待受理订单录入订单池；工作人员可抢单、接受指派、提交完成凭证，但不能因全品牌授权获得客服职能。本次未将 `enterOrder` 开放给工作人员。

代码发现客服与工作人员原先共用 `uni` 的 `token/user/accessProfile` 存储键。多个工作台标签页切换账号时可能覆盖会话，而已打开页面仍保留旧的客服视图。日志能证明当前请求身份为工作人员，但不能仅据此确认是哪个标签页或哪次登录造成。

本次修复：工作台 H5 改为按标签页、独立命名空间存储完整会话；登录时校验所选身份与返回角色，再原子保存；旧请求响应不会覆盖切换后的账号页面；录入按钮依据服务器 `allowedActions` 显示，提交时再次检查当前角色；后端返回明确的 `ROLE_FORBIDDEN`，而非笼统“会话未授权”。

部署新版 `game-service` 和 workbench H5 后，旧通用登录信息不再迁移，请在客服标签页重新使用真实客服账号登录。需要同时调试工作人员时，另开一个标签页登录工作人员即可。若某手机号在后台实际登记为“工作人员”，请使用/创建客服账号；点击“客服登录”不会自动改变账号角色。请勿继续传播日志中的完整会话 token。

按本次确认：**客服和工作人员默认授权所有品牌**，包括 `demo-a`、已有其他品牌以及后续新品牌，无需管理员逐个授权。新旧账号均适用，上传新版阿里云 `game-service` 后，已有有效会话的下一次请求也会应用；过期会话仍需重新登录。

- 开关：`code/apps/client/uniCloud-aliyun/cloudfunctions/game-service/lib/staff-brand-access.cjs` 中 `STAFF_ALL_BRANDS = true`。不需要新增环境变量，也不向数据库批量写入永久 `*` 权限。
- 客服可处理所有品牌订单；工作人员可查看所有品牌抢单池、接受所有品牌指派，但“我的订单”、提交凭证、钱包仍限制为本人。客户小程序仍按客户身份和品牌隔离。
- 账号停用、接单冻结、角色矩阵、支付核验不变。全品牌授权不等于管理员权限。
- 后台账号管理显示“所有品牌（联调默认）”，归档品牌只为日后恢复隔离保留。客服列表仍可主动按单一品牌筛选；要查看全部，请选“全部授权品牌”并清空状态等筛选。
- 部署：上传 `game-service`，重发 admin/workbench H5；本次无需重发客户端小程序。无需再执行下文“给 demo-a 手动授权”的步骤。
- 正式隔离运营前，将开关改为 `false` 并重新上传，系统改按数据库原有品牌授权读取；旧会话中曾签发的 `*` 不会继续被当成持久授权。届时按下文账号管理流程配置所需品牌。

以下保留原流程设计与实施记录；其中手工品牌授权步骤只在关闭当前联调策略时适用。

本次策略调整验证：38 项支付/工作流/授权专项检查通过，admin 与 workbench 生产构建通过。尚未上传云端，实际生效以部署后的接口和账号验证为准。

## 一、问题与实施边界

支付完成进入 `PENDING_ACCEPT` 后，客服列表调用 `game-service.listOrders`，不是支付接口。

代码已确认的缺口：

- 员工账号创建页没有明确的品牌选择、已有员工没有就近授权入口。默认创建到 `default`，而当前商品和订单属于 `demo-a`，客服的品牌权限过滤可能得到空列表。实际云端账号授权还需通过后台核对，不能仅凭截图断言。
- 订单查询使用数据库默认条数，再在内存过滤品牌，可能漏掉较新的订单；页面把异常响应直接转成空数组，且返回列表时没有刷新。
- 受理、指派、验收共用的事务使用 `where().update()`，不符合阿里云事务限制；结单还有事务内条件查询钱包的问题。
- 工作人员订单复用了客户精简 DTO，丢失履约字段；管理端缺少直接受理、验收和结单入口。

只修改阿里云实现及四端源代码，保留原生支付、支付回调验签、金额核验和品牌隔离。不将已付款状态人工伪造，不自动给客服授予全部品牌权限。

## 二、状态约定

| 状态 | 展示 | 执行者与下一步 |
| --- | --- | --- |
| PENDING_PAYMENT | 待支付 | 用户支付，服务端确认真实交易 |
| PENDING_ACCEPT | 待受理 | 客服或管理员补全需求并放入订单池 |
| PENDING_GRAB | 待抢单 | 工作人员抢单，或客服/管理员指派 |
| ASSIGN_PENDING | 待指派确认 | 已选定工作人员，等待其接受或拒绝 |
| IN_SERVICE | 服务中 | 工作人员执行服务并提交完成凭证 |
| PENDING_CONFIRM | 待验收 | 客服/管理员验收；退回则回服务中；通过后确认客户结果并结单 |
| SETTLED | 已结单 | 用户查看结果，工作人员查看佣金，管理端追溯记录 |

沿用已有数据模型：用户所说“待指派”在人工分配分支对应“待指派确认”，不是另造一个无接单人的状态。抢单成功可以直接进入服务中；人工指派必须经工作人员确认。拒绝指派、退单回到订单池。保留退款、异议和取消分支，不能强行将所有订单串成不可回退的七步。

## 三、实施任务

### 阶段一：订单可见与可靠流转

1. 管理端账号创建明确选品牌；员工行可查看和添加品牌授权。为 `demo-a` 客服/工作人员显式授权后重新登录。
2. 客服列表显示当前授权品牌，提供品牌筛选、明确的空态原因与错误，返回页面刷新；订单查询完整读取分页，不再受默认 100 条截断影响。
3. 共用状态转换改成事务内读文档、验证状态/版本、更新文档和写日志；结单在事务外定位钱包，事务内重新读取并一次性入账，重复结单不能重复发佣金。

### 阶段二：四端履约闭环

1. 客服：受理表单预填已有信息，按订单品牌选择工作人员，支持待确认指派的改派、验收和结单。
2. 工作人员：返回页面更新订单，展示履约字段，在“我的订单”直接接受/拒绝指派并提交凭证。
3. 管理员：订单详情直接补齐受理信息、指派/改派、验收通过/退回、确认结单。
4. 用户端：七阶段进度及状态文案一致，返回页面查询服务器状态，不在前端擅自推进状态。
5. 必要日志仅记录 action、订单 ID、状态及版本，不打印联系方式、令牌或支付密钥。

## 四、上线顺序及验收

1. 上传阿里云 `game-service`（包含修改后的 lib）。不上传腾讯云目录。
2. 重新构建并发布 admin、workbench、client H5；重新编译/上传客户端小程序。
3. 管理员进入账号管理，选择 `星河服务（demo-a）`，给实际客服和工作人员添加对应授权；退出后重新登录工作台。此操作只改变授权，不搬迁或修改历史订单品牌。
4. 用已付款订单验证：客服可见 → 受理进池 → 人工指派/工作人员接受（另核对抢单分支）→ 提交凭证 → 验收通过 → 勾选客户已确认并结单。
5. 检查用户端、工作人员、客服、管理员状态一致；重复结单不重复入账、无品牌权限不可查看或操作。

本地检查不能替代云端数据库、真实账号和四端联合验收；部署及实际授权未执行前不能宣称线上已修复。

## 五、本次实施结果（2026-09-13）

阶段一、二的源代码已落地：

- 后台账号管理新增品牌选择和员工行“授权所选品牌”；授权列表不受顶部当前品牌筛选影响，避免未授权员工根本找不到。
- 客服订单列表展示授权范围、可选品牌、加载中与异常提示；返回列表/详情重新查询。管理端补齐待支付筛选。
- 订单、员工和授权查询显式分页；接口保留原有数组返回值。单次兼容查询最多读取 9900 条，超过则明确提示缩小范围，不静默截断。大量历史数据后仍应改成前后端分页接口。
- 受理/抢单/接受指派/验收/退回改成文档事务并检查版本；改派补上事务内状态检查。结单在同一事务更新订单、钱包与流水，确定性佣金流水 ID 防重复。
- 工作人员订单 DTO 补回 UID、区服、要求、产出单位和验收退回原因；“我的订单”直接接受/拒绝指派。接受指派也检查账号、接单开关、钱包接单冻结和当前任务数量。
- 管理端详情新增受理、验收通过、退回及勾选客户已确认后结单。客服可在指派待确认/服务中改派。
- 用户端拆分七阶段筛选与进度，异常/退款订单不错误展示为已结单。自主抢单无需走人工指派确认步骤。
- 修正工作人员上传 `fileId`/`fileID` 大小写不一致，上传时传订单 `bizId`；提交前校验凭证所属人员、品牌、业务类型和有效文件 ID。两端验收从订单凭证 ID 获取临时访问链接，原始存储 ID 不回传。

验证结果：支付与工作流专项检查 **33 项通过**；管理员 H5、工作台 H5、客户端 H5、客户端微信小程序构建通过；修改范围差异格式检查通过。未修改 `uniCloud-tcb`，未上传云函数、未修改云端账号授权或真实订单。

阿里云事务写法依据：[DCloud 数据库事务限制](https://doc.dcloud.net.cn/uniCloud/cf-database.html#start-transaction)。

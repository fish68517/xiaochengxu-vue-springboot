## 1. 规划结论

第二批工作的目标不是重做现有系统，也不是继续进行大面积视觉改版，而是在现有功能、领域模型、多端 UI 和本地验证体系之上，补齐真实商用所必需的安全、资金、合规、运维和真实环境证据。

第二批完成后的目标状态定义为：

> 系统达到“可进入真实 staging 验收并具备小流量灰度运营条件”的商用候选版本。只有真实云环境、真实域名、真实微信链路、真实支付/退款、备份恢复演练和合规材料全部验收后，才能批准生产上线。

本批次必须坚持增量开发：

- 保留 `packages/domain` 的领域规则单一源，不复制或另起一套业务逻辑；
- 保留客户 H5/小程序、客服/接单工作台、管理后台三端现有结构和 UI Batch 0～6 成果；
- 保留 `game-service` 云函数与本地镜像后端的契约一致性；
- 在现有验证脚本、部署脚本、品牌配置、审计和回滚能力上补强；
- 所有最终代码继续在 `code` 目录内完成；
- 本地/Mock 通过、staging 通过、production 通过必须分开记录，禁止用本地构建代替真实商用验收。

## 3. 上线前必须先确定的业务决策

商用 Batch 0 必须形成书面决策记录。未决事项可以开发接口和适配层，但不得直接进入生产。

| 决策项 | 推荐首发方案 | 原因 | 最迟确认时间 |
|---|---|---|---|
| 品牌法律主体 | 首发品牌采用同一法律主体、一个生产空间、一个微信支付商户主体 | 降低数据、资金和备案复杂度 | Batch 0 结束前 |
| 多品牌隔离 | 同主体使用逻辑隔离并强制 `brandCode`；不同主体使用独立空间、数据库和支付账户 | 避免跨主体数据和资金混用 | Batch 0 结束前 |
| 支付模式 | 首发采用普通商户直连；暂不默认启用服务商分账 | 当前业务规模下更易验收和对账 | Batch 5 开始前 |
| 提现模式 | 首发采用“双人复核 + 线下合规出款 + 回单登记”；自动出款作为后续可插拔通道 | 在未确认渠道资质前避免伪自动化 | Batch 6 开始前 |
| 实名方式 | 优先接入合规实名服务并最小化保存身份证原文 | 降低敏感数据长期存储风险 | Batch 4 开始前 |
| 退款权限 | 明确自动退款阈值、客服可审批上限、财务复核上限 | 防止越权退款和资金损失 | Batch 6 开始前 |
| 未成年人策略 | 明确是否允许未成年人使用、可用时段、消费限制和申诉流程 | 影响注册、实名和支付规则 | Batch 4 开始前 |
| 数据保留 | 明确订单、审计、实名材料、附件、客服记录的保留周期 | 决定清理任务和归档策略 | Batch 4 开始前 |
| 故障目标 | 建议首发 RPO ≤ 24 小时、RTO ≤ 4 小时，最终以负责人批准值为准 | 作为备份、恢复和告警验收依据 | Batch 7 开始前 |
| 灰度范围 | 先内部员工，再 5～20 名受控客户，再逐步扩大 | 降低资金和服务履约风险 | Batch 9 开始前 |

## 4. 第二批总体阶段划分

第二批划分为三个阶段、10 个增量开发 Batch。编号使用“商用 Batch”，避免与此前 UI Batch 混淆。

| 阶段 | Batch | 核心目标 | 阶段出口 |
|---|---|---|---|
| 第二批第一阶段：阻断项修复 | 商用 Batch 0～4 | 决策冻结、链路修复、系统入口保护、认证升级、隐私合规 | 不再存在可由普通用户触发的系统任务；核心账户和 PII 达到 staging 安全基线 |
| 第二批第二阶段：资金与可靠性闭环 | 商用 Batch 5～7 | 微信支付、退款/提现/对账、告警/备份/CI/性能 | 真实 staging 可完成小额支付、退款、人工出款闭环和恢复演练 |
| 第二批第三阶段：真实环境与灰度 | 商用 Batch 8～9 | 真实部署、域名/微信配置、全链路验收、灰度运营 | Go/No-Go 评审通过后方可进入生产灰度 |

推荐总工期为 8～12 周，按 2 名开发、1 名测试/运营兼职、法务和财务按节点参与估算。备案、微信审核、支付开户、域名和第三方实名服务的外部周期不计入纯开发工期，应从 Batch 0 起并行办理。

### 商用 Batch 1：正式 API 与客户链接链路

**目标**

保证客户 H5、小程序、工作台和管理后台在 staging/production 使用正确的正式 API 与页面链接，不再依赖本机地址或错误路由。

**主要任务**

- 统一 H5 订单链接生成器，实际地址必须采用 `/#/pages/h5-order/index?token=...`；
- 修复本地镜像后端、`game-service` 和微信回调中不一致的 H5 链接；
- 将前端 API transport 按 `API_MODE` 明确区分 local 和 uniCloud；
- production 构建发现 `127.0.0.1`、`localhost` 或 Mock transport 时直接失败；
- 对 H5 token 增加品牌、订单、过期时间、用途和单次/撤销策略校验；
- 校验 Hash 路由刷新、深链打开、微信内打开和普通浏览器打开；
- 增加链接泄露后的失效和重新签发能力；
- 对 URL 查询参数中的敏感字段进行最小化，禁止把身份证号、手机号等放入链接。

**预计改动位置**

- `packages/backend/src/services.js`
- `uniCloud-tcb/cloudfunctions/game-service/lib/services.cjs`
- `uniCloud-tcb/cloudfunctions/wechat-callback/index.js`
- `apps/client/src/shared/api.*`
- `apps/workbench/src/shared/api.*`
- `apps/admin/src/shared/api.*`
- `scripts/release-preflight.mjs`
- 对应单元测试和 E2E 脚本

**交付物与验收**

- 三处服务端生成的订单链接契约一致；
- 手机微信内、手机浏览器、桌面浏览器均能从完整链接进入目标订单；
- 无效、过期、跨品牌、已撤销 token 均返回明确且不泄露订单数据的错误；
- staging 三端请求均到真实 uniCloud，不出现本机地址；
- 新增链接契约测试、Hash 路由 E2E 和 production 配置负向测试。

### 商用 Batch 2：系统任务、回调与后台入口保护

**目标**

消除普通用户触发定时任务、内部补偿任务、支付回调或后台系统 action 的可能性。

**主要任务**

- 将 `transferNotify`、订单超时关闭、服务池超时、指派超时等系统 action 与普通 API 分离；
- 定时任务只允许 uniCloud 定时触发器或具有签名的内部调用；
- 内部调用使用时间戳、nonce、HMAC/平台凭证和重放保护；
- 微信支付/退款回调执行平台签名验签、证书序列号检查、时间窗检查、幂等检查；
- 生产环境禁止通过前端 API 直接提交“支付成功”“出款成功”状态；
- 高风险操作记录操作者、来源 IP、请求 ID、前后值和结果；
- 为后台 action 建立显式角色/权限矩阵；
- 增加跨品牌访问、越权审批、重放回调和伪造内部调用负向测试。

**预计改动位置**

- `uniCloud-tcb/cloudfunctions/game-service/lib/auth.cjs`
- `uniCloud-tcb/cloudfunctions/game-service/index.js`
- `uniCloud-tcb/cloudfunctions/game-service/lib/services.cjs`
- `uniCloud-tcb/cloudfunctions/wechat-callback/index.js`
- 本地镜像后端对应认证/服务文件
- 定时触发器配置、审计 schema 和测试文件

**交付物与验收**

- 普通登录用户调用任何系统 action 均被拒绝；
- 未签名、签名错误、过期、重复 nonce 的内部请求均被拒绝；
- 重复支付回调不会重复记账；
- 所有资金状态改变可通过 `requestId/eventId` 追溯；
- 权限矩阵测试覆盖客户、客服、接单人员、财务、管理员和系统身份。

### 商用 Batch 3：账户安全、密码迁移与高权限认证

**目标**

将当前适合演示的登录机制升级为可商用账户安全基线，并兼容现有账号平滑迁移。

**主要任务**

- 将无盐快速 SHA-256 密码升级为 Argon2id 或 scrypt；如运行环境限制，使用经评审的自适应慢哈希实现；
- 采用“登录成功后渐进迁移”兼容旧密码，不保存或记录明文密码；
- 增加全局持久化登录失败计数、账户/IP/设备多维限流和指数退避；
- 管理员、财务和可退款/出款角色启用 MFA；
- 增加会话版本、强制下线、密码修改后全端失效、管理员封禁和登录历史；
- Session Cookie/Token 按端设置安全属性、过期、刷新和撤销机制；
- 增加弱密码检测、初始密码强制修改和敏感操作二次验证；
- 前端统一错误提示，不暴露账号是否存在、散列算法或内部错误；
- 增加爆破、撞库模拟、旧密码迁移和会话撤销测试。

**预计改动位置**

- `uniCloud-tcb/cloudfunctions/game-service/lib/auth.cjs`
- `packages/backend/src/services.js` 及本地镜像认证实现
- 用户/会话/登录事件相关数据库 schema
- `apps/workbench/src/pages/login/*`
- `apps/admin/src/pages/login/*`
- 管理员安全设置页面和测试

**交付物与验收**

- 新密码不再使用无盐快速哈希；
- 旧账号可登录并自动升级散列，新旧过程可回滚且不暴露密码；
- 管理员和财务未完成 MFA 时不能执行高风险操作；
- 多实例情况下限流仍生效，不能通过重启云函数绕过；
- 会话撤销后旧 token 立即失效；
- 认证安全测试和审计事件测试全部通过。

### 商用 Batch 4：PII、附件、协议与用户数据权利

**目标**

形成“最少采集、加密保存、受控查看、到期清理、可查询/更正/注销”的个人信息处理闭环。

**主要任务**

- 建立 PII 字段目录，标记手机号、身份证号、实名材料、地址、支付标识和客服附件；
- 服务端实施字段级加密，密钥与数据分离，支持密钥版本和轮换；
- 对确需查询的字段建立不可逆盲索引，禁止用明文敏感字段做普通索引；
- 默认接口只返回脱敏值，查看完整信息需特权、二次确认、用途记录和审计；
- 附件改为私有存储，使用短时签名 URL，校验扩展名、MIME、大小和恶意文件；
- 增加用户协议、隐私政策、儿童/未成年人规则、服务交易规则、退款规则展示页；
- 记录协议版本、同意时间、来源和撤回状态；
- 实现账号注销申请、冷静期、阻断条件、执行和结果通知；
- 实现个人信息副本申请、更正、删除/匿名化和申诉工单；
- 根据批准的数据保留期限实现归档/清理任务，并提供 dry-run 报告；
- 对测试日志、错误日志、URL、埋点和导出文件增加敏感信息扫描。

**预计改动位置**

## 9. 数据库与迁移专项要求

第二批涉及认证散列、PII 加密、资金状态和审计字段，数据库变更风险较高，统一按以下规则实施：

1. 所有 migration 先支持 dry-run，并输出影响记录数、异常记录和预计耗时；
2. 先新增字段并双写/兼容读取，再迁移旧数据，最后在确认窗口移除旧读取路径；
3. 不直接覆盖原始 PII；先备份、加密写入新字段、抽样核验，再按批准计划清除旧字段；
4. 密码只做登录时渐进迁移，无法解密或反推出旧密码；
5. 资金数据迁移必须校验迁移前后总额、订单数、流水数和哈希摘要；
6. 每个 migration 必须有幂等性、断点续跑、失败重试和回滚说明；
7. production migration 必须先在生产同构数据副本演练；
8. migration 执行前记录备份 ID，执行后保存日志和校验报告；
9. 大表索引采用不阻塞核心业务的方式，并在低峰窗口执行；
10. 任何金额不平或跨品牌污染都必须停止迁移，不允许“先上线再修”。

## 11. 商用发布硬门禁

出现下列任一情况，结论必须为 No-Go：

- 仍有普通用户可触发系统任务、支付通知或出款通知；
- 支付、退款、钱包、提现或渠道账单存在无法解释的金额差异；
- 存在跨品牌读取、操作或支付串用；
- production 构建仍包含 localhost、Mock 支付、演示 Secret 或默认密码；
- 密码仍使用无盐快速 SHA-256，或管理员/财务未启用 MFA；
- 身份证等 PII 仍以可直接识别的明文长期保存且无批准例外；
- 隐私政策、用户协议、退款规则、账号注销和投诉渠道未上线；
- 微信支付回调未验签、未幂等或不能主动查单补偿；
- 真实备份未启用，或隔离恢复演练未成功；
- 告警不能真实送达值班人员；
- 未取得所需备案、微信审核、支付权限或主体授权；
- staging 未通过真实支付/退款和端到端验收；
- 没有可执行的回滚包或数据库变更不可安全回滚；
- 财务、法务、运营、测试或技术负责人拒绝签字。

## 12. 每个商用 Batch 的统一完成定义

一个 Batch 只有同时满足以下条件才可标记完成：

- 范围内代码和文档均已提交，未混入无关重构；
- 领域规则仍以 `packages/domain` 为单一源，生成文件未手改；
- 单元测试、负向测试、幂等测试和权限测试随代码一同新增；

- 数据库变更提供 migration、dry-run、回滚和数据校验；
- 新配置已进入 `.env.example`/配置契约，但真实 Secret 未进入仓库；
- 安全、资金和 PII 操作均有审计记录；
- 验收证据进入固定目录并含时间、环境、版本和执行人；
- 未完成项明确记录负责人、风险、临时措施和最后期限；
- 对应业务、财务、法务或运维负责人完成必要签字。

## 13. 人员与职责建议

| 角色 | 主要职责 |
|---|---|
| 技术负责人 | 架构、Secret、云部署、安全门禁、回滚、最终技术签字 |
| 后端开发 | 认证、权限、支付、退款、提现、对账、PII、定时任务 |
| 前端开发 | 三端正式 API、MFA、协议/注销、财务与审计交互、错误态 |
| 测试负责人 | 回归、负向、并发、真实支付、品牌隔离、证据归档 |
| 产品/运营 | 业务规则、履约、投诉、客服、灰度范围和 SLA |
| 财务负责人 | 商户配置、退款/提现审批、对账和资金验收 |
| 法务/合规 | 协议、隐私、实名、未成年人、数据保留和主体边界 |
| 发布管理员 | production 权限、CI 审批、版本发布、回滚执行 |

高风险操作应执行职责分离：开发人员不应单人同时拥有 production 数据库写权限、支付 Secret 管理权限和发布审批权限。

## 14. 推荐实施顺序与近期动作

本计划批准后，建议按以下顺序开始实施：

1. 立即执行商用 Batch 0，冻结单主体/多主体、支付和提现方案；
2. 外部并行启动 DCloud 实名、域名备案、微信认证、商户权限和协议审查；
3. 先完成商用 Batch 1 和 Batch 2，修复真实链接和系统入口，这是进入任何公网环境前的最低安全条件；
4. 接着完成商用 Batch 3 和 Batch 4，处理账户和个人信息；
5. 安全基线通过后再接真实微信支付，执行 Batch 5；
6. 支付稳定后完成 Batch 6 的退款、提现和对账；
7. Batch 7 的监控、备份和 CI 应与 Batch 5～6 交叉推进，但必须在 staging 验收前完成；
8. Batch 8 完成真实 staging 部署和全链路证据；
9. 只有所有硬门禁通过后，才执行 Batch 9 的生产灰度。

首个编码迭代建议控制在商用 Batch 0～2，不要同时大规模改动密码、PII 和资金模型，以降低回归和迁移风险。

> Batch 1 上线兼容性说明：安全升级后，历史上缺少 `purpose/jti` 的 H5 token 将被拒绝。staging/production 切换时必须由客服重新生成并发送存量未完成订单链接，不迁移或继续放行旧 token。

## 15. 第二批完成后的后续方向

第二批结束并不代表平台运营成熟。灰度稳定后再规划第三批商业增长能力，例如：

- 服务供应者准入评分、培训、排班和质量管理；
- 客诉仲裁、赔付、保险和服务质量 SLA；
- 营销、优惠券、渠道归因和活动风控；
- 财税、发票和结算报表深化；
- 服务商模式、自动分账或合规自动出款；
- 多地域容灾、更高 RPO/RTO 和容量扩展；
- 数据分析、留存、复购和品牌经营看板；
- 外部安全测评、渗透测试和持续合规审计。

这些能力必须建立在第二批的安全、资金、合规和运维底座之上，不应提前挤占商用 P0 项的开发资源。
